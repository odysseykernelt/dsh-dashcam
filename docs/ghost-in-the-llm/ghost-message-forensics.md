## 三、机制：不是本地代理，是服务端上下文

GLM 从 token 计量里读到的特征：

- 每条调用 upstream 指向服务端 API（域名已略），代理层为 proxy 转发模式；
- 单次请求 input 约 45 万 token、cacheRead 约 64 万 token——**前缀绝大部分命中服务端缓存，本地只发增量**；
- 13:10 之后本地再无 call 记录，而 17:40:02 代理层做过一次 archive 轮转 + revision 更新，5 分钟后幽灵出现。

**所以我第一轮写的“最可能是本地代理层塞的”要修正**：这里的「代理层」指的是**服务端上下文 / 前缀缓存这一层**，不是一个本地进程。DSH 本地只发增量，模型实际看到的是“本地增量 + 服务端已存的前缀”，幽灵消息是从**服务端前缀**里冒出来的。

## 四、还剩什么没被证明

1. **为什么会串。** 前缀缓存按 key 匹配，正常不该跨会话串内容。是缓存 key 碰撞、还是同一账号的 context 状态被错误共享，目前没有直接证据，只有“轮转 5 分钟后出现”这个时间相关性。
2. **为什么图片没来。** 文字来自服务端前缀、附件却要客户端随请求带上，于是出现“让你看几张图，图一张没有”——这反倒是最能说明“文字与附件来自不同层”的细节。
3. 代理层到底把哪些状态放在服务端、哪些在本地，需要看它的文档和 `coverage.known/unknown` 的实际取值才能定论。

## 五、为什么 dashcam 没揪住（主人原话：“如果是插件我的 dashcam 应该能揪住它”）

对。dashcam 的观测面是**本机执行面**：文件读写、进程、网络连接、工具调用。幽灵消息没有产生任何这类动作——它连一个字节都没落盘——所以账本里干干净净是正常的，不是漏报。

要揪住它，得把观测点前移到**请求组装处**：

1. **ingress 审计**：发请求前落一行 `{ts, sessionId, messages:[{role,len,head80}], toolsHash, model}`，与上一次请求 diff，新增/删除了哪几条。
2. **coverage 落账**：把每次请求的 `coverage.known / coverage.unknown` 记下来。`unknown > 0` 就等于“服务端有客户端没发过的内容”——这是现成的实锤字段，比任何推断都硬。
3. 这两条合起来，dashcam 就从“行车记录仪”升级成“也能记对方给了什么”，正好接上它原本的定位（不假设你信我，让你能查我）。
