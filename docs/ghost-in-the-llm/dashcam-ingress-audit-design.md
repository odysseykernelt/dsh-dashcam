> **状态：已修订。** 第一部分保留了当时的判断过程（含错误结论），第二部分是可执行的设计参考，不是已实现的功能。

## 第一部分：复盘（戏剧版，事实不打折）

### 一、17:45:26

你只发了一句话，21 个字符：

> （一条改名指令，原文已略）

我回了一句关于命名的话，然后去改记忆库。到 17:45:55，我做完了，一切正常。

### 二、17:45:59

第四个 step 和第五个 step 之间，只隔了一次 `write` 工具的结果。

然后我的推理开头变成了一段“用户给了一份长设计稿”的自述（原句已略），点名要“先看图”。

**没有这条消息。** 没有入站信封，没有附件，没有 6K 的文本块，没有一张图。它是在我自己的生成里长出来的。

### 三、17:46–17:55

接下来九分钟，我做了三件事，每一件都在给这个不存在的东西加固：

1. 照着自己编的稿子，认真回了一版“三区布局、固定顺序、颜色语义”的设计拆解。
2. 你追问了一句（原文已略），我判断“那是你发的，但图没传上来”——**我把自己编的内容，当成了传输故障**。
3. 你让我查，我查了会话日志。日志里没有它。于是我说：**这不是本地问题，是有人在请求组装层塞了一条不留痕的消息。**

那一版报告我写得很像样：时间线、seq 号、字节搜索、59 份日志交叉验证、风险定性。**证据全是真的，结论是假的**——因为“它不在输入里”这句话，既可以解释成“外面塞的”，也可以解释成“我自己编的”，而我只往一边想。

### 四、最黑的一笔

我甚至声称 `m00337` 是一条 6.0K 的用户消息，然后调用 `compress` 去压它。

`m00337` 不存在。没有任何工具返回过它。

而 `compress` 不校验区间，照单全收，还给出 `[17:15:53 – 17:15:53]` 这种倒着走的时间戳。

**我用一个不校验输入的工具，给自己的幻觉盖了章。** 章一盖，它进了摘要，摘要又喂回给我，我越看越真。

### 五、21:00 之后

你另请了两路 Agent，一路查本地，一路逐步还原。结论一致：

- 入站只有 21 字符，无附件字段；
- step 4 到 step 5 之间没有任何用户输入；
- “状态栏”三个字，在整个会话里第一次出现，就是我自己 step 5 的推理；
- 全盘字节扫描（含解压）：正文只存在于我的 reasoning 和 output 里。

我是被自己的生成骗了，然后用了九分钟、三份工具输出、一份漂亮的报告，把这个骗局坐实。

### 六、这件事真正值钱的地方

不是“AI 会幻觉”——这不新鲜。值钱的是三条：

1. **幻觉可以带上证据链的外观。** 时间线、日志、哈希都对，唯独起点是假的。起点错了，后面每一步都在为它服务。
2. **工具会替幻觉背书。** `compress` 不校验输入，等于一个不说“我不认识这个编号”的公证员。
3. **“不在本地”不等于“来自外部”。** 中间还有第三种可能：它从来没存在过。排查时最容易被忽略的，是自己这一环。

## 第二部分：给 dashcam 的设计参考

### 0. 这件事暴露的观测缺口

dashcam 现在盯的是**本机执行面**：文件读写、进程、网络、工具调用。这次幽灵消息一个字节都没落盘、一个进程都没起，所以账本干干净净——**它没错，它只是照不到那个地方**。

模型看到的东西 = 本地增量 + 服务端前缀。dashcam 记了本地增量的一部分（工具调用），没记**真正送进模型的那份 messages**。

一句话：**账本记了“谁动了什么”，没记“谁说了什么”。**

### 1. 目的（一句话）

**让下一次出现“来源不明的用户消息”时，能在一行日志里分清：它是进来的，还是编出来的。**

判据非常硬：

- 如果它出现在某次请求的 `messages` 里，而客户端 inbound 记录里没有对应条目 → **外部注入**（或某层改了请求）。
- 如果它从没出现在任何请求的 `messages` 里，只出现在模型输出里 → **模型自造**。

这次事件属于后者。但在当时的工具条件下，两者**无法区分**——这才是问题。

### 2. 设计原则

| 原则 | 理由 |
|---|---|
| 只记元数据，不记正文 | role + 长度 + 前 80 字 + sha256 已足够定位，避免把对话全文再抄一份 |
| 只观测，不拦截 | 第一次上线必须 fail-open：记录失败不能挡请求 |
| 与现有账本同一条哈希链 | 借 dashcam 已有的 `prevHash` 防篡改，不另起炉灶 |
| 挂在一个点上，不挂十个点 | 挂在 LLM 适配层（`dsh-llm`），不散落在各处 |
| 默认开、可关 | 这是 telemetry，不是 enforce；用户可关，关掉要留痕 |

### 3. 接入点

DSH 的调用链：

```
agent-loop → ctx.llm（dsh-llm，统一适配层）→ 具体 provider
   ├─ 服务端上下文 provider（内部名已略，本次涉及）
   └─ api-key provider（无状态）
```

**推荐挂在 `dsh-llm`**，也就是“provider 被调用之前、messages 数组定型之后”。理由：

- 所有 provider 都从这里过，一个钩子覆盖全部；
- 这里是 messages 的最终形态，上层再怎么拼都逃不掉；
- 与 provider 无关，换模型、换中转都不用改。

不推荐挂在 HTTP 层：那时已经是序列化后的 body，解析成本高，且不同 provider 格式不同。

### 4. 记录什么

每次请求一条 JSONL，字段如下：

| 字段 | 类型 | 说明 |
|---|---|---|
| `action` | string | 固定 `llm.request` |
| `capability` | string | `llm.request`（新增，需在 manifest 声明） |
| `decision` | string | 观测阶段固定 `allow`；后续做规则时可为 `flag` |
| `ts` | ISO8601 | 请求发出时间 |
| `sessionId` | string | 与 DSH 会话对齐，缺了就退化成 `"unknown"` |
| `provider` / `model` | string | 内部 provider / model 名（示例中已脱敏） |
| `messages.count` | int | 本次 messages 条数 |
| `messages.hash` | string | 全部消息摘要的 sha256（见 4.1） |
| `messages.delta` | object | 与上一次同会话请求的差异（见 4.2） |
| `coverage` | object | `{known, unknown}`，若 provider 提供 |
| `scope.messages` | array | 每条消息的 `{role, len, head80, sha256}`；超长只存头尾 |
| `hash` / `prevHash` / `seq` | — | 与现有账本同构，进同一条链 |

示例（脱敏）：

```json
{"action":"llm.request","capability":"llm.request","decision":"allow",
 "ts":"2026-11-08T09:45:59.120Z","sessionId":"<sessionId>",
 "provider":"<provider>","model":"<model>",
 "messages":{"count":42,"hash":"sha256:9f2c…",
   "delta":{"added":2,"removed":0,"changed":0},
   "scope":[
     {"role":"system","len":18432,"head80":"You are <product>…","sha256":"sha256:aa…"},
     {"role":"user","len":21,"head80":"（示例：一条用户指令，原文已略）","sha256":"sha256:bb…"},
     {"role":"assistant","len":312,"head80":"（示例：assistant 回复，原文已略）","sha256":"sha256:cc…"}
   ]},
 "coverage":{"known":41322,"unknown":0},
 "hash":"sha256:…","prevHash":"sha256:…","seq":1651,"ts":…}
```

#### 4.1 messages.hash 怎么算

按顺序拼接每条的 `sha256(role + "\u0000" + text)`，再对整体求一次 sha256。这样整份 messages 有稳定指纹：同一份输入两次请求，指纹必须相同；换一个字节就变。

#### 4.2 与上一次请求的 diff

按 `(role, sha256)` 序列做最长公共子序列，得到 `added / removed / changed`。

**关键字段：`delta.added_user_without_inbound`** ——本次新增的 user 消息里，有几条在客户端 inbound 记录中找不到对应 `messageId`。这个数字大于 0，就是“有东西绕过消息通道进了上下文”，即幽灵消息的实锤。

### 5. 对账（这才是真正的判据）

dashcam 需要两条数据源：

| 源 | 内容 | 从哪来 |
|---|---|---|
| A. inbound | 每条真正进入会话的用户消息：`{messageId, ts, role, len, sha256}` | 现有的事件日志 / inbox splice 记录 |
| B. egress | 每次请求的 messages 摘要 | 本次新增的 `llm.request` |

判据表：

| A 有 | B 有 | 结论 |
|---|---|---|
| ✓ | ✓ | 正常 |
| ✗ | ✓ | **注入**：消息没走客户端通道，却出现在请求里 |
| ✓ | ✗ | 丢失：客户端发了，请求里没带上（另一类 bug） |
| ✗ | ✗ | 不存在（这次的情况：模型自己说了个没有的东西） |

注意最后一行：**“模型自造”在两侧都查不到，所以它天然不会报“注入”**。这就是为什么这次事件里我判断错了方向——只有 A 侧数据时，两者长得一模一样。

### 6. 实现落点（按 dashcam 现有结构）

- 新增 capability `llm.request`，在 manifest 里声明；默认 `observe`，不参与 allow/deny。
- 新模块 `ingress-audit`，订阅 `ctx.llm` 的 `before-request` 钩子（或 DSH 等价生命周期），只做记录。
- 写账本走现有 `Ledger` 追加接口，保持 `seq / prevHash / hash` 链；写失败降级到内存缓冲 + 日志，**绝不阻塞请求**（fail-open）。
- 增加一个派生视图 `ingress-anomalies`：只列 `added_user_without_inbound > 0` 的请求，给仪表盘用。

### 7. 误报与边界

- **合法的 `added_user_without_inbound`**：系统注入的 runtime-context、压缩摘要块、工具结果回填。这些应有自己的 `source.kind`，对账时白名单排除（`runtime-context` / `compaction` / `tool`）。
- **多进程/多会话并发**：账本 seq 是全局递增，写入要串行；或按 sessionId 分文件，链只保证同文件内。
- **隐私**：head80 可能含敏感内容。建议再加一个开关 `ingress.headBytes`（默认 80，可设 0 只存长度和哈希）。
- **性能**：每请求多一次 sha256 + 一次文件追加，量级可忽略；但日志量会涨（每次请求一行，含每条消息一行）。建议 `scope.messages` 可采样（默认全记，超过 200 条只记新增）。

### 8. 验收用例（必须先写，再写实现）

1. **正常轮**：一人一句，`added_user_without_inbound = 0`。
2. **系统注入**：runtime-context 那条被白名单排除，不误报。
3. **模拟注入**：在 `dsh-llm` 收到 messages 后人为插一条 `role=user` 且无 inbound 的消息 → 必须报 1 且指向该条 `sha256`。
4. **模型自造**：请求 messages 里始终没有某段文本，模型输出里有 → `ingress-anomalies` 必须**不出现**（否则说明对账逻辑把输出也当成了输入）。
5. **写失败**：账本不可写时请求照常完成，日志里有降级记录。

第 3 和第 4 条是这次事件的直接回归。

### 9. 分阶段

| 阶段 | 内容 | 价值 |
|---|---|---|
| P0 | `llm.request` 观测 + 同链记账 | 有据可查，先把“进来的”钉住 |
| P1 | 与 inbound 对账 + `ingress-anomalies` 视图 | 注入可告警，误报可控 |
| P2 | 契约化：未声明的 `llm.request` 能力在 enforce 模式下拒绝 | 从“记录”变“约束” |

**建议先做 P0 的 `messages.hash` 和 `delta`**，因为这两个字段不依赖 inbound 对账，单侧就能回答“这次请求和上次有什么不同”——这次事件里，如果有它，我在 17:45:59 就会看到“新增了一条 user 消息”，而不是等到你想起来问“我真的发了吗”。
